# ClipDownloader Phase 설계 운영 규칙

## 1. 목적과 기준 문서

이 문서는 ClipDownloader의 Phase별 상세 설계 시작 조건, 명세 변경 처리, 대화 context별 역할과 문서 인계 기준을 정의한다. 현재 작업 대상은 ClipDownloader이며, 구현 단계와 완료 조건은 기존 요구사항을 따른다.

설계의 공통 기준은 다음 문서다.

- [제품 요구사항](requirements/01_PRODUCT_REQUIREMENTS.md)
- [아키텍처 원칙](requirements/02_ARCHITECTURE.md)
- [구현 단계와 완료 조건](requirements/03_IMPLEMENTATION_PLAN.md)
- [저장소 전략](requirements/README_FOR_REPOSITORY.md)
- [Codex 작업 지침](requirements/README_FOR_CODEX.md)
- [프로젝트 구조 설계](PROJECT_STRUCTURE_DESIGN.md)

사용자의 최신 명시 지시를 우선한다. 문서 간 충돌이 작업에 영향을 주면 충돌과 영향을 기록하고 해소한 뒤 해당 부분을 확정한다. 대화 기억이나 가정을 명세 변경으로 취급하지 않는다. 다른 context에서 내린 결정은 근거와 함께 기준 문서에 기록하여 전달한다.

## 2. 기본 진행 원칙

> Phase n의 상세 설계는 Phase n−1이 현재 유효한 명세 기준으로 구현·검증을 완료하고, 다음 Phase에 영향을 주는 미해결 사항이 정리된 뒤 시작한다. 명세 변경 시에는 영향 분석을 먼저 수행한다. 이후 Phase의 요구사항·연결 지점에 대한 사전 검토는 허용한다.

- Phase 0은 선행 구현 단계가 없으므로 요구사항과 전체 구조를 기준으로 상세 설계를 시작한다.
- Phase n−1 구현 중에는 Phase n의 상세 설계를 시작하거나 확정하지 않는다.
- 사전 검토는 후속 요구사항, 계층 경계, 재사용할 계약, 위험 요소 확인으로 제한한다. 구체적인 API·클래스·알고리즘·패키지 선택을 후속 Phase의 확정 설계로 만들지 않는다.
- 현재 Phase를 구현하기 위해 필요한 연결 계약은 현재 Phase 설계에 기록한다. 미래 요구만을 이유로 기능이나 추상화를 선행 구현하지 않는다.
- 여러 Phase의 상세 설계를 동시에 진행하지 않는다. 전체 구조 설계는 공통 기준과 장기 연결 지점을 담당한다.
- 설계 완료와 구현 완료를 구분한다. 상세 설계 작업만으로 코드 작성·프로젝트 생성·의존성 설치까지 승인되었다고 해석하지 않는다.

## 3. 다음 Phase 상세 설계 시작 조건

다음 조건을 모두 확인한다.

1. 이전 Phase의 필수 구현 및 완료 조건을 충족했다.
2. 관련 빌드·테스트·실행 검증을 실제로 수행했고 결과를 기록했다. 요구된 실제 동작 검증을 실행할 수 없다면 완료로 간주하지 않는다.
3. 구현 결과와 확정된 설계 결정이 문서에 반영되어 있다.
4. 명세 변경이 있다면 현재 기준에 대한 영향 분석과 필요한 선행 보완을 완료했다.
5. 다음 Phase에 영향을 주는 차단 사항이 없다. 남은 비차단 사항은 이유, 영향, 처리 시점을 기록했다.
6. 다음 Phase 설계가 사용할 소스 상태와 기준 문서를 식별할 수 있다.

Git commit을 사용할 수 있으면 기준 commit을 기록한다. 미커밋 작업이 있다면 그 사실과 관련 변경 파일을 함께 기록한다. 문서 작성을 위해 임의로 commit하지 않는다.

필수 완료 조건을 임의로 제외하거나 실패한 검증을 성공으로 기록하지 않는다. 검증을 생략했다면 생략 이유와 아직 확인되지 않은 사항을 명시한다.

## 4. 명세 변경이 없는 경우

```text
Phase n−1 상세 설계
  → 구현
  → 필수 검증
  → 결과·결정·미해결 사항 기록
  → 시작 조건 확인
  → Phase n 상세 설계
```

다음 Phase는 계획된 API를 추정해서 사용하지 않고, 이전 Phase에서 실제로 구현하고 검증한 계약과 동작을 기준으로 설계한다.

이전 Phase에서 발견한 기술적 제약이 제품 요구와 충돌하면 명세 변경 필요 여부를 검토한다. 단순 구현 선택 변경과 제품 요구 변경을 구분한다.

## 5. 명세 변경이 발생한 경우

변경 발생만으로 모든 작업을 중단하거나 전체 Phase를 다시 수행하지 않는다. 먼저 변경 내용, 영향받는 단계·계약·완료 조건을 확인한다.

| 영향 범위 | 처리 방법 | 다음 Phase 시작 조건 |
|---|---|---|
| 문구·명칭 등 기능과 계약에 영향 없음 | 관련 문서를 정리하고 기준 갱신 | 기존 완료 조건 유지 |
| Phase n 이후에만 영향 | 진행 중인 Phase n−1을 계속하고 후속 요구 기록 | 이전 Phase 완료 후 변경 명세로 설계 |
| 진행 중인 Phase n−1에 영향 | 해당 설계·완료 조건 갱신 후 필요한 구현과 검증 수행 | 변경된 기준으로 이전 Phase 완료 |
| 이미 완료된 Phase에 영향 | 영향받는 부분의 보완 설계·구현·검증 수행 | 선행 보완 완료 후 진행 |
| 공통 구조나 여러 Phase에 영향 | 전체 구조 설계와 영향받는 Phase 문서를 먼저 조정 | 관련 계약·선행 구현의 일관성 확보 |

변경에 의존하는 작업은 수정된 기준이 정리될 때까지 진행하지 않는다. 독립적인 작업은 계속할 수 있다.

이미 확정한 상세 설계가 변경 영향을 받으면 재검토 상태로 표시하고, 필요한 부분만 수정한다. 이전 결정은 변경 이유를 이해할 수 있도록 기록한다.

명세 변경 기록에는 다음을 포함한다.

- 변경 내용과 근거: 사용자 지시, 수정된 요구사항 문서 등
- 영향받는 Phase, 프로젝트, 공개 계약, 완료 조건
- 기존 구현을 유지할 수 있는 부분과 보완해야 하는 부분
- 필요한 검증과 실제 결과
- 다음 설계에 사용할 갱신된 기준

## 6. 대화 context 분리와 문서 인계

### 전체 설계 context

현재 대화는 공통 기준 문서, 프로젝트 경계, Phase 간 연결과 충돌, 명세 변경의 영향을 판단하는 전체 설계 context로 사용한다. Phase별 설계가 기존 요구사항과 일치하는지 검토하고, 전체 구조 변경이 필요하면 이유와 영향을 정리한다.

### Phase별 context

별도의 새 대화 context는 지정된 한 Phase의 상세 설계에 집중한다. 기존 기준과 이전 Phase의 실제 결과를 읽고, 범위·책임·계약·완료 조건을 구체화한다. 해당 Phase의 구현을 요청받으면 같은 context에서 구현과 검증까지 이어서 진행한다. 후속 Phase 기능이나 ClipEditor 개발을 임의로 추가하지 않는다.

Phase 0은 요구사항과 전체 구조를 기준으로 새 context를 시작할 수 있다. Phase n은 Phase n−1의 구현·검증 완료와 제3절의 시작 조건을 확인한 뒤 새 context에서 상세 설계를 시작한다. 이전 context가 존재하거나 종료되었다는 사실만으로 이전 Phase가 완료되었다고 판단하지 않는다.

이 운영 방식은 대화 context를 분리하는 것이다. 새 context가 이전 대화의 내용이나 결정 근거를 자동으로 전달받는다고 가정하지 않는다. 기준과 결정은 문서로 연결하며, 이 문서 자체로 새 대화 생성이나 구현 작업을 실행하지 않는다.

### 새 context 시작 시 인계 자료

새 context에는 다음 자료의 경로와 필요한 요약을 제공한다. 요약은 원본 문서를 대체하지 않으며, 작업 시작 시 해당 파일을 읽어 현재 기준을 확인한다.

1. 대상 Phase와 작업 종류: 설계 또는 구현
2. 현재 유효한 요구사항, 전체 구조 설계, 이 문서인 `docs/ClipDownloader/PHASE_DESIGN.md`
3. 이전 Phase의 상세 설계와 구현·검증 결과
4. 기준 소스 상태 및 미커밋 변경 사항
5. 명세 변경 기록, 미해결 사항, 변경 가능한 파일 범위
6. 기대 산출물과 제외 범위

### context 전환 전 기록

현재 Phase의 결정 사항, 선택 이유, 실제 구현·검증 결과, 미해결 사항과 다음 Phase에 영향을 주는 제약을 문서에 반영한 뒤 인계한다. 폐기한 선택지는 재검토를 막거나 trade-off를 설명하는 데 필요한 경우에만 이유와 함께 남긴다.

한 문서의 동시 편집은 피한다. 공통 기준 변경이 필요한 경우 제안과 영향을 먼저 기록하고 전체 설계 context에서 정합성을 확인한다. 명시적으로 승인된 변경이나 현재 작업 범위의 통상적인 설계 선택에 대해 불필요하게 승인을 반복 요청하지 않는다.

## 7. Phase 상세 설계 문서의 필수 항목

파일은 `docs/ClipDownloader/phases/PHASE_N_DESIGN.md` 형식으로 작성한다. 실제 해당 Phase의 상세 설계를 시작할 때 생성하며, 미래 Phase용 빈 문서를 미리 만들지 않는다.

각 문서는 다음 항목을 포함한다.

- **목표와 범위**: 이번 Phase에서 달성할 동작과 제외할 기능
- **기준과 시작 조건**: 사용한 명세, 소스 상태, 이전 Phase 완료 근거
- **현재 구조와 변경 계획**: 영향받는 프로젝트·파일·참조 관계
- **상세 책임과 계약**: 필요한 모델·서비스·UI 상태·데이터 흐름
- **설계 결정**: 선택 근거, 의미 있는 대안과 trade-off
- **실행 계획**: 의존성을 고려한 구현 순서
- **완료 조건과 검증**: 각 요구사항을 확인할 빌드·테스트·실제 동작 검증
- **미해결 사항**: 사실과 가정 구분, 차단 여부, 검증·처리 시점
- **인계 사항**: 다음 Phase가 사용할 계약과 제약
- **변경 기록과 상태**: 설계 중, 설계 확정, 구현 중, 구현·검증 완료, 재검토 필요 중 해당 상태

설계에는 검증 계획을 기록하고, 구현 후에는 같은 문서의 결과 항목에 실제 수행 결과를 추가한다. 예정된 명령이나 기대 동작을 완료 증거로 사용하지 않는다.

## 8. 적용 범위와 현재 상태

이 문서는 Phase 설계 운영 규칙을 정의하며, 각 Phase의 실제 완료 여부는 [Phase Baseline](PHASE_BASELINE.md)과 해당 Phase의 실제 검증 기록을 따른다.
