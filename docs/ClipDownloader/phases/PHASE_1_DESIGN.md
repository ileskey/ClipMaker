## 1. 목표와 범위

URL, Start, End, Output path를 받아 단일 MP4 클립을 만드는 CLI/Core prototype을 설계한다. Timecode, 공통 ProcessRunner, 공식 지원 URL 판별, yt-dlp 메타데이터, 원격 구간 획득, 공통 FFmpeg 처리, 출력 검사와 취소가 대상이다.

WPF 다운로드 UI, 큐, Preview, 브라우저 연동, 로컬 파일 사용자 기능, ClipEditor, 자동 도구 다운로드·업데이트, 인증 UI는 제외한다.

## 4. 결정한 정책과 선택 근거

여기서 ‘결정’은 이번 설계의 적용 정책이다. 기술 가정의 실증 또는 전체 설계 확정과 구분한다. 제품 요구를 바꾸는 사용자 지시가 생기면 영향 분석 후 갱신한다.

### 4.1 시간과 FPS

- 입력은 기존 전체 구조의 **시계 시간 + 프레임 오프셋**: `HH*3600 + MM*60 + SS + FF/FPS`. SMPTE non-drop/drop-frame을 도입하지 않는다. 정식 SMPTE는 장시간 소수 FPS 표시에 의미가 있지만 현재 요구와 표시 의미가 달라 별도 요구 변경이 필요하다.
- 구간은 `[Start, End)`이며 Start >= 0, End > Start, End <= Duration을 같은 시간 기준에서 검사한다. 시간은 24시간을 넘어도 허용하고 분·초는 0~59, 프레임은 0 <= FF < 실제 FPS로 검사한다. 자릿수·공백·syntax/semantic 구분은 제4.7절의 채택한 규칙을 따른다.
- FPS는 양의 유리수로 보존한다. ffprobe의 분자/분모를 우선하고, 소수 메타데이터는 원래 소수값을 유리수로 표현한다. `29.97`을 근거 없이 `30000/1001`로 바꾸지 않는다. 표준 FPS 추정은 이번 기본 정책에서 제외한다.
- 내부 유리수 계산에서 오차를 누적하지 않는다. TimeSpan 경계는 가장 가까운 tick, 정확히 중간이면 짝수 반올림을 적용하고 overflow는 입력 오류로 처리한다. 구간 검증은 가능하면 tick 반올림 전 값으로 한다.
- 시간→연속 프레임 번호는 내림한다. 이 프레임 번호를 시간코드 문자열과 동일한 것으로 취급하지 않는다. 소수 FPS의 역변환 문자열이 항상 같다는 보장은 하지 않는다.
- FPS는 선택된 video format 기준이다. 누락 시 ffprobe 확인을 시도하고, 끝내 확인할 수 없으면 FPS 기반 타임코드 입력을 실패시킨다. 임의의 30fps 또는 사용자 추정 FPS로 조용히 대체하지 않는다.
- VFR·CFR 미확인 입력에서 평균 FPS는 표시·시간 변환에 사용할 수 있으나 실제 프레임 번호 보장은 하지 않는다. Accurate의 성공·제한 정책과 CFR 판정 범위는 시간축 실험 후 확정한다. 단순히 r_frame_rate와 avg_frame_rate가 같다는 이유로 CFR라고 단정하지 않는다.

### 4.2 포맷·모드·출력

- 기본 모드는 Fast로 계획한다. Phase 2 UI 초안과 일치하며 재인코딩 비용을 피한다. Accurate는 사용자가 명시 선택한다. 처리 중 자동 모드 변경은 금지한다.
- 화질 기본은 Best이며 명시 해상도는 실제 제공 목록에서 선택한다. 제공되지 않는 해상도를 조용히 낮추거나 높이지 않는다. format 선택은 video/audio 조합을 보존한다.
- Best의 우선순위와 Fast 복사 가능 코덱 목록은 실제 도구 확인 후 확정한다. 이름만 Best로 표시하고 내부적으로 호환성 때문에 화질을 낮추는 경우 선택 결과와 이유를 드러내야 한다.
- Accurate의 초기 출력 후보는 H.264/AAC, 전체 선택 구간 재인코딩이다. 부분 재인코딩·하드웨어 가속·hybrid trim은 제외한다. 실제 인코더 지원 확인 전 확정된 실행 가능 기능으로 간주하지 않는다.
- ffprobe는 입력 시간축과 결과 검사의 필수 도구로 둔다. 누락 시 검사를 생략하지 않고 MissingTool을 반환한다. 파일 크기나 확장자만으로 결과 성공을 판정하지 않는다.
- 최종 출력은 MP4, 기존 파일 덮어쓰기 금지. 작업별 임시 폴더와 같은 출력 볼륨의 staging을 사용하고 검사 후 최종 파일로 확정한다. 이동 순간의 충돌도 처리한다.
- 명시 출력 경로는 사용자 의도를 바꾸지 않도록 잘못된 이름을 오류로 반환한다. 자동 생성 이름만 Windows 금지 문자·예약 이름·끝 공백/마침표 등을 정리한다. 실패·취소 staging은 완성 결과가 아니다. 정리 실패는 원래 오류를 덮지 않고 기록한다.

### 4.3 원격 획득과 시간축

- 우선 실험 후보는 yt-dlp `--download-sections`로 구간을 임시 미디어로 획득하고 공통 처리에 전달하는 경로다. 전체 구조의 기본 경계와 일치한다.
- 원본/로컬 시간축 관계는 별도 증거로 확인한다. 요청 section_start 또는 임시 파일 start_time=0은 실제 첫 프레임의 원본 위치 증거가 아니다.
- 재인코딩을 두 번 수행하는 경로를 기본으로 삼지 않는다. yt-dlp 단계에서 이미 수행한 trim/mux와 이후 FFmpeg 처리 필요를 구분한다.
- 시간축 보존이 불가능하면 직접 원격 스트림 FFmpeg 처리 등 대안을 비교하되, 공통 계층에 사이트 로그인·플랫폼 정책을 넣지 않는다. 경계 변경이 필요하면 전체 구조에 대한 영향부터 기록한다.
- 전체 원본 다운로드 fallback은 추가하지 않는다. 시간축·정확도를 확인하지 못한 입력을 Accurate 성공으로 반환하지 않는다.

공식 근거: [yt-dlp 옵션](https://github.com/yt-dlp/yt-dlp#usage-and-options)은 시간 구간 다운로드와 FFmpeg 의존성을 제공한다. [FFmpeg seek 문서](https://www.ffmpeg.org/ffmpeg.html#Main-options)는 stream copy와 재인코딩의 seek 동작 차이를 설명한다. 이 문서만으로 특정 사이트의 실제 시간축을 확정할 수는 없다.
### 4.4 프로세스·취소·진단

- 공통 ProcessRunner를 Media.Infrastructure에 둔다. shell 없이 ArgumentList로 실행하고 stdout/stderr를 동시에 읽는다. 메타데이터 JSON과 진행률은 서로 다른 출력 계약으로 처리한다.
  - 후속 2b E3 결과로 Windows backend는 생성 시 Job 연결이 가능한 CreateProcessW를 사용한다. argv 목록·shell 비사용 원칙은 유지하고 Windows CRT quoting을 실제 인자 보존 테스트로 검증한다. 근거·최종 수명 정책은 [2b 실제 결과](PHASE_1_STAGE_2B_RESULT.md)를 따른다.
- 출력 누적은 상한을 둔다. JSON 상한 초과는 잘린 JSON을 파싱하지 않고 명시 실패로 처리한다. 다운로드 로그는 지속 drain과 제한된 진단 보관으로 메모리 증가를 막는다. 상한·타임아웃은 제4.11~4.12절의 채택한 값을 따른다.
- Ctrl+C → 작업 token → 외부 프로세스 종료 요청 → 종료/스트림 정리 → staging 정리 → 결과 → 로거 정리 순서를 사용한다. 취소 token으로 정리 대기 자체를 즉시 중단하지 않는다.
- `Kill(entireProcessTree: true)`와 root 종료 대기를 최소 구현 후보로 사용하되 자식 종료 보장으로 표현하지 않는다. 자식 생존·파이프 유지 사례를 별도 검증하고 잔존 문제가 있으면 Windows Job Object 등 보완을 검토한다. 지금부터 네이티브 수명 관리 전체를 선행 도입하지 않는다.
- 도구 탐색 Found는 파일 존재뿐이다. 실행 실패·버전·필요 인코더 확인을 분리하고 Phase 0 경로 우선순위·명시 경로 자동 대체 금지는 유지한다.
- 오류는 구조화된 코드와 입력/실행 오류 분류로 구분하고 취소는 별도 결과다. 채택한 CLI 종료 코드는 제4.6절, 세부 오류 계약은 제4.19절을 따른다.
- 원시 진단은 민감값 제거 후 기록한다. 서명 URL·쿠키·인증값이 포함될 수 있는 명령/JSON 전체를 로그에 남기지 않는다.

[Microsoft Process.Kill 문서](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0)는 root 종료 대기가 모든 descendant의 종료 대기가 아님을 명시한다. 실제 취소 완료 기준은 root뿐 아니라 시작된 자식과 부분 파일을 포함한다.

### 4.5 지원 입력·도구 준비

- 공식 CHZZK VOD, YouTube watch, youtu.be만 허용한다. 호스트·경로·ID를 검사하고 URL에 사용자 인증정보가 있거나 형식이 잘못되면 거부한다. URL 정규화는 제4.8절을 따른다. ID의 최종 기본 문자 검사와 Uri 정규화 경계 사례는 구현 전 통합 계약에 명시한다.
- 단일 완료 영상이 대상이다. 라이브·재생목록 전용·접근 불가·DRM 콘텐츠는 명확한 오류로 처리한다. watch URL에 playlist 파라미터가 함께 있어도 영상 하나만 대상으로 한다.
- 메타데이터의 길이와 사용 가능한 video format은 추출에 필수다. 누락된 uploader·thumbnail은 추정하지 않고 상태를 보존한다. 제목·FPS 누락 처리는 제4.9절, 비정상 JSON 처리는 제4.10절을 따른다.
- 기존 세 도구 외 YouTube JavaScript 의존성을 준비 항목에 포함한다. [yt-dlp 공식 의존성](https://github.com/yt-dlp/yt-dlp#dependencies)에 따라 실제 설치 버전의 EJS·JS runtime 요구를 확인한다. 자동 설치·원격 구성요소 다운로드·쿠키 import는 기본 동작에 넣지 않는다.
- JS runtime 종류·경로 전달·배포는 실제 환경 확인 후 최소 필요만 결정한다. 새 generic ToolLocator를 재사용할 수 있지만 Phase 0 WPF 진단 화면에 도구를 임의로 추가하지 않는다.

### 4.6 CLI 계약 — 사용자 채택 완료

2026-10-09 사용자가 다음 명령·옵션·종료 코드를 명시적으로 채택했다.

| 명령 | 역할 |
|---|---|
| diagnose | 도구 경로·실행 가능 여부·버전 확인 |
| info | 영상 메타데이터와 선택 가능한 화질 조회 |
| clip | 단일 구간을 MP4로 생성 |

info는 `--url`이 필수다. clip은 `--url`, `--start`, `--end`, `--output`이 필수이며 출력 경로에는 MP4 파일명까지 포함한다. 선택 옵션 `--quality`는 기본 `best` 또는 info에 표시된 해상도(예: `720p`), `--mode`는 기본 `fast` 또는 `accurate`다.

공통 도구 경로 옵션은 `--yt-dlp-path`, `--ffmpeg-path`, `--ffprobe-path`다. 생략하면 기존 탐색 정책을 사용한다. JS runtime 옵션은 실험 결과에 따라 별도로 결정한다.

정상 결과는 stdout, 진행 상황·경고·오류는 stderr로 출력한다. info는 사람이 읽을 수 있는 요약을 제공한다. JSON 출력 옵션은 현재 범위에 추가하지 않는다.

| 종료 코드 | 의미 |
|---|---|
| 0 | 성공 |
| 1 | 도구 누락·사이트 조회·처리·결과 검사 등 실행 실패 |
| 2 | 옵션·URL·시간 구간·출력 경로 등 입력 오류 |
| 130 | 사용자 취소: Ctrl+C, 확인 단계의 N·빈 입력·공백 입력·EOF |

130은 Unix CLI의 SIGINT 종료 관례를 채택한 애플리케이션 정책이며 Windows가 자동 부여하는 값이라는 의미가 아니다. CLI가 Ctrl+C를 처리하여 작업·프로세스·파일 정리를 수행한 뒤 반환한다. 오류 상세는 Application 오류 코드와 메시지로 구분하며 외부 도구의 종료 코드를 그대로 CLI 종료 코드로 전달하지 않는다.

근거: [Bash 종료 상태](https://www.gnu.org/software/bash/manual/html_node/Exit-Status.html), [Windows Ctrl+C 이벤트](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent).

#### clip 실행 전 표시·확인 — 사용자 채택한 CLI 계약 변경

2026-10-09 사용자가 다운로드 전 메타데이터·작업 요약을 표시하고 Y/N 확인을 받으며, `--yes` 지정 시에는 확인 입력을 기다리지 않고 진행하는 방식을 채택했다. 초기 CLI 계약에 이 동작과 clip 전용 플래그를 추가한다.

- clip은 메타데이터 조회 후 항상 영상 정보·작업 요약·확인된 주의사항을 표시한다. 제목·영상 ID·플랫폼·업로더·전체 길이, 선택 해상도·FPS·영상/음성 코덱·음성 유무, IN/OUT·클립 길이·모드·출력 경로를 포함한다. 누락되거나 아직 검사하지 않은 값은 미확인으로 표시하며 추정값을 확정 정보로 표시하지 않는다.
- 기본 확인 문구는 `위 설정으로 클립을 생성하시겠습니까? [y/N]`다. Y/N을 받고 기본 응답(Enter)은 취소다. Y를 받은 뒤 구간 획득·출력 생성을 시작한다.
- `--yes`는 같은 요약·주의사항을 표시하되 확인 대기를 생략한다. 입력 검증이나 실행·결과 검사 생략 옵션이 아니다.
- 비대화형 실행에서 `--yes`가 없으면 입력을 기다리지 않고 확인이 필요하다는 오류로 종료 코드 2를 반환한다.
- 확인 전에 알 수 있는 잘못된 구간·필수 정보 누락 등 차단 오류는 Y로 우회하지 않는다. 원격 획득 이후에만 확인 가능한 정보는 확인 화면에서 미확인으로 표시하고 이후 검사에서 판정한다. 정확한 사전 검사 범위는 획득/FPS 실험 결과와 연결한다.
- 확인 응답의 앞뒤 공백을 제거하고 Y/y는 진행, N/n 또는 빈 입력(Enter만 입력하거나 공백만 입력)은 취소한다. 그 외 입력은 Y/N 안내 후 재입력을 받는다. EOF는 진행하지 않고 취소한다. 사용자가 이 규칙을 채택했으며 N·빈 입력·EOF·Ctrl+C는 모두 종료 코드 130을 사용한다. 이는 기존 Ctrl+C 전용 취소 코드를 사용자 취소 전반으로 확장한 결정이다.
- 확인 메시지는 제4.15절에 따라 stderr로 출력한다. 사전 검사 가능 범위는 FPS·획득 실험으로 보완한다. 비대화형 실행은 확인 대기 전 코드 2로 거부하며, EOF의 코드 130 규칙은 실제로 확인 입력을 받기 시작한 경우에 적용한다.

### 4.7 타임코드 입력·파싱 — 사용자 채택 완료

2026-10-09 사용자가 다음 규칙과 syntax/semantic 2단계 검사를 채택했다.

| 항목 | 규칙 |
|---|---|
| 형식 | 콜론으로 구분한 HH:MM:SS:FF 네 필드 |
| HH | 최소 2자리, 24시간 이상 허용 |
| MM / SS | 정확히 2자리, 각각 00~59 |
| FF | 최소 2자리, 0 이상 실제 FPS 미만 |
| 숫자 | ASCII 0~9만 허용 |
| 공백 | 앞뒤 공백 제거, 내부 공백 거부 |
| 기타 표기 | 부호·소수점·세미콜론·생략형 거부 |
| 표시 | 시간·프레임 최소 2자리, 분·초 2자리로 정규화 |

1단계 syntax 검사는 구분자·필드 수·문자·자릿수를 확인한다. 2단계 semantic 검사는 MM/SS의 고정 범위, 선택 포맷 FPS에 대한 FF 범위, 실제 시간 계산, Start/End 관계와 영상 길이를 확인한다. MM/SS 범위 검사는 FPS 없이 먼저 실행할 수 있으나 책임상 semantic 검사에 속한다. 이는 앞선 제안의 1단계에 함께 설명했던 필드 범위 검사를 사용자가 표현한 syntax/semantic 구분에 맞춰 명확히 배치한 것이다.

잘못된 값을 다음 초로 자동 이월하거나 영상 끝으로 자르지 않는다. 오류에는 해당 필드와 허용 범위를 표시한다. 파싱·계산 범위를 넘는 큰 값은 입력 오류다. 30fps의 00:00:10:15는 10.5초, FF=30은 오류다. 120fps의 00:00:00:100과 100:00:00:00은 허용하며 0:0:10:0은 자릿수 오류다.

타임코드 문법·의미 검사는 Media.Core에서 호스트와 독립적으로 재사용한다. CLI 옵션 파싱과 영상 전체에 대한 작업 검증은 각각 CLI와 Application 책임이다. 반환 타입·시그니처는 모델 계약 검토에서 정한다.

### 4.8 URL 검증·정규화 — 사용자 채택 완료

2026-10-09 사용자가 다음 규칙을 채택했다.

- https만 허용한다. 앞뒤 공백은 제거하고 내부 공백은 거부한다. 사용자명·비밀번호 포함 URL과 기본 HTTPS 포트 외 포트는 거부한다.
- 호스트는 정확한 허용 목록으로 비교한다. CHZZK는 chzzk.naver.com의 /video/{숫자 ID}, YouTube는 youtube.com/www.youtube.com/m.youtube.com의 /watch?v={ID}, 단축 URL은 youtu.be/{ID}를 허용한다.
- Shorts·embed·라이브·재생목록 전용 URL 등 다른 경로는 현재 지원하지 않는다. watch URL에 list가 있어도 v의 영상 하나만 처리한다. 중복 v는 모호한 입력으로 거부한다.
- 정규화 결과는 https://chzzk.naver.com/video/{ID} 또는 https://www.youtube.com/watch?v={ID}다. 추적 파라미터·fragment·URL 시작 시간은 제거한다. 추출 시간은 --start/--end만 사용한다.
- ID는 기본 문법만 검사한다. 실제 영상 존재·접근 가능 여부와 완료 영상 여부는 yt-dlp 조회로 확인한다. URL 문법 통과와 소스 조회 성공은 구분한다.

3a에서 ID 문자·길이, 원문 경로/authority, percent decode/중복 key 경계를 구체화했다. 실제 구현·수정한 runtime 가정·테스트는 [3a 결과](PHASE_1_STAGE_3A_RESULT.md)를 따른다. YouTube는 11자리 ASCII 영문/숫자/_/-, CHZZK는 비어 있지 않은 ASCII 숫자 문자열이며 임의 영상 존재 여부를 추정하지 않는다.

### 4.9 메타데이터 누락 처리 — 사용자 채택 완료

2026-10-09 사용자가 다음 누락 정책을 채택했다. 확인 화면에는 모든 항목을 표시하며 누락된 정보는 미확인으로 표시한다.

| 항목 | 누락 시 처리 |
|---|---|
| 영상 ID | 조회 실패 |
| 제목 | 제목 없음 표시, 자동 파일명에는 ID 사용 |
| 길이 | info는 표시 가능, clip은 구간 검증 불가로 거부 |
| FPS | 추가 검사 시도, 끝내 확인 불가하면 clip 거부 |
| 업로더·썸네일·업로드 날짜 | 미확인 표시, 진행 허용 |
| 영상 포맷 | 사용 가능한 포맷이 없으면 clip 거부 |
| 해상도 | 해당 포맷의 해상도 지정 선택 불가 |
| 코덱 | 추가 검사 후 해당 모드의 처리 가능 여부 판단 |

음성 유무 미확인과 실제 음성 스트림 없음은 구분한다. 아직 불명확하면 미확인, 실제 음성 스트림이 없는 영상이면 음성 없음을 표시하고 무음 클립 생성을 허용한다. 음성이 있는 원본에서 출력 음성이 누락되는 것은 허용된 무음 입력과 구분하여 결과 검사에서 다룬다.

Y/N은 안내된 작업의 실행 여부를 선택하는 단계이며 Y나 --yes로 필수 정보 누락을 우회하지 않는다. FPS·코덱 등의 추가 검사 시점과 방법은 획득/시간축 실험에 따라 구체화한다. JSON 오류·비정상 필드·개별 포맷 제외 규칙은 제4.10절의 채택한 계약을 따른다.

### 4.10 JSON·비정상 데이터 처리 — 사용자 채택 완료

2026-10-09 사용자가 전체 응답 실패와 일부 필드/포맷 오류를 구분하는 다음 규칙을 채택했다.

| 상황 | 처리 |
|---|---|
| JSON 문법 오류·출력 잘림 | 조회 실패 |
| 최상위가 단일 영상 객체가 아님 | 조회 실패 |
| 알 수 없는 추가 필드 | 무시 |
| 필수 영상 ID가 비어 있거나 잘못된 타입 | 조회 실패 |
| 제목·업로더 등 선택 정보의 잘못된 값 | 미확인 처리, 진단 기록 |
| 음수 길이·0 이하 FPS·잘못된 해상도 | 미확인 처리 후 제4.9절 누락 정책 적용 |
| 개별 포맷 ID 누락·중복 | 해당 포맷 제외, 진단 기록 |
| 사용 가능한 포맷이 모두 제외됨 | info에 사유 표시, clip 거부 |

숫자 필드는 JSON 숫자만 허용하며 문자열 숫자를 임의로 변환하지 않는다. 잘못된 필드와 포맷 제외 사유를 진단에 남기되 인증값·서명된 스트림 URL이 포함될 수 있는 JSON 전체는 저장하지 않는다. 출력 상한과 수집 방법은 ProcessRunner 세부 계약에서 정한다.

### 4.11 프로세스 출력 수집·메모리 상한 — 사용자 채택 완료

2026-10-09 사용자가 stdout/stderr 동시 수집과 다음 보관 정책을 채택했다.

| 출력 용도 | 처리 |
|---|---|
| yt-dlp·ffprobe JSON | 전체 수집, 스트림당 최대 32MiB |
| 다운로드·FFmpeg 진행률 | 읽는 즉시 해석, 전체 누적하지 않음 |
| 오류 진단용 stdout/stderr | 각각 마지막 256KiB 보관 |
| 진단 보관 상한 초과 | 오래된 내용 제거, 생략 사실 표시 |
| JSON 상한 초과 | 프로세스 정리 후 명시적 실패, 잘린 JSON 파싱 금지 |

보관 상한과 스트림 drain은 분리한다. 진단 보관이 가득 차도 읽기를 계속하며 JSON 상한 초과에 따른 중단에서도 프로세스 종료·스트림 정리를 수행한다. 전체 원시 출력을 로그에 복제하지 않고 민감값을 제거한 진단과 단계별 결과를 기록한다.

32MiB와 256KiB는 표준값이나 실제 샘플 검증 결과가 아닌 채택한 초기 설계값이다. 실제 검증에서 조정 필요가 확인되면 근거와 함께 변경한다. Phase 1에서는 내부 상수로 두고 CLI 설정 옵션을 추가하지 않는다. 상한의 바이트 계산·디코딩 경계는 상세 ProcessRunner 계약에 명시한다.

### 4.12 타임아웃 — 사용자 채택 완료

2026-10-09 사용자가 다음 초기 제한 시간과 처리 규칙을 채택했다. Phase 1에서는 내부 정책으로 두며 변경 옵션은 추후 추가한다. 현재 CLI 옵션이나 설정 저장 기능으로 선행 구현하지 않는다.

| 작업 | 제한 시간 |
|---|---|
| 도구 버전·지원 기능 확인 | 프로세스 호출당 15초 |
| yt-dlp 메타데이터 조회 | 호출당 120초 |
| 로컬 파일 ffprobe 검사 | 호출당 60초 |
| 원격 구간 획득·FFmpeg 처리 | 고정 제한 없음, 사용자 취소 지원 |
| 중단 후 프로세스·스트림 정리 | 별도 10초 |

제한 시간은 프로세스 실행 직전부터 측정한다. 타임아웃이면 종료를 요청하고 별도 정리 시간을 적용한다. 타임아웃은 사용자 취소와 구분하여 실행 실패 코드 1로 반환한다. 정리 시간까지 초과하면 종료 확인 실패를 보고하며 성공·정상 취소로 표시하지 않는다. 사용 중일 수 있는 임시 파일은 무리하게 삭제하지 않는다.

다운로드·인코딩에 고정 제한을 두지 않으며, 출력이 없다는 이유만으로 중단하는 무응답 타임아웃도 Phase 1에서는 제외한다. 위 시간은 실제 검증 결과가 아닌 초기 설계값이며 조정 필요가 확인되면 근거를 기록한다.

### 4.13 취소·완료 경합 — 사용자 채택 완료

2026-10-09 사용자가 다음 취소 및 최종 확정 정책을 채택했다.

| 상황 | 처리 |
|---|---|
| Y/N 대기 중 취소 | 코드 130, 구간 획득 시작하지 않음 |
| 다운로드·처리·검사 중 취소 | 새 단계 진입 차단, 프로세스 종료·정리 후 코드 130 |
| 최종 파일 확정 직전까지 취소 수락 | staging 정리, 최종 파일 생성하지 않음 |
| 최종 파일 확정이 시작된 이후 취소 | 확정 결과를 따름: 성공 0, 실패 1 |
| 프로세스 종료 확인 실패 | 정상 취소로 처리하지 않고 코드 1 |
| 프로세스는 종료됐지만 임시 파일 삭제 실패 | 코드 130 유지, 남은 경로와 정리 실패 안내 |

최종 확정은 검사를 마친 staging 파일을 최종 경로로 이동하는 단계다. 단계 진입과 취소 수락은 한 지점에서 조정하며 최종 확정 진입 후에는 취소로 되돌리지 않는다. 이미 확정한 파일은 뒤늦은 취소로 삭제하지 않는다. 확정 실패는 실행 실패로 처리한다.

취소 처리 중에는 취소 중 상태를 표시한다. 반복 Ctrl+C는 같은 취소 요청으로 처리하며 두 번째 Ctrl+C로 정리를 건너뛰는 강제 종료 기능은 추가하지 않는다. 종료 확인 실패와 파일 정리 실패는 구분한다. 구체적인 동기화·수명 계약은 ProcessRunner와 Application 모델 설계에서 명시한다.

### 4.14 출력 경로·작업 공간 — 사용자 채택 완료

2026-10-09 사용자가 다음 구체적인 출력 정책을 채택했다.

| 항목 | 처리 |
|---|---|
| 상대 출력 경로 | CLI를 실행한 현재 디렉터리 기준으로 절대경로 변환 |
| 확장자 | .mp4 필수, 대소문자 구분 없음 |
| 출력 폴더 | 기존 폴더만 허용, 자동 생성하지 않음 |
| 명시한 파일명 | Windows에서 유효하지 않으면 오류, 자동 수정하지 않음 |
| 기존 출력 파일 | 확인 전에 입력 오류로 거부, 코드 2 |

도구 상대 경로는 기존 AppContext.BaseDirectory 기준을 유지하며 출력 상대 경로와 구분한다. 확인 화면에는 최종 출력 절대경로를 표시한다.

획득한 임시 미디어는 사용자 앱 데이터 아래 작업 ID별 폴더에 둔다. 최종 검사 대상 staging은 출력 폴더에 고유한 임시 이름으로 생성하고 검사 통과 후 요청한 최종 이름으로 이동한다.

Y/N 확인 전에는 경로 형식·폴더 존재·파일 충돌을 검사한다. 쓰기는 확인 이후 시작하며 실제 쓰기 권한·디스크 공간 등의 실행 중 실패는 실행 오류로 처리한다. 성공·실패·취소 후에는 해당 작업이 생성한 임시 파일만 정리한다. 정리 실패는 원래 결과를 덮지 않고 남은 경로를 안내한다. 프로세스 종료 미확인 시에는 제4.12~4.13절의 보존 정책을 우선한다.

### 4.15 CLI 메시지·진행률 — 사용자 채택 완료

2026-10-09 사용자가 다음 출력 위치와 진행 표시를 채택했다.

| 메시지 | 출력 위치 |
|---|---|
| info 메타데이터·diagnose 진단 결과 | stdout |
| clip 실행 전 영상 정보·작업 요약 | stdout |
| Y/N 질문·재입력 안내 | stderr |
| 진행률·주의사항·오류·취소 안내 | stderr |
| 생성 완료 및 최종 파일 경로 | stdout |

진행 단계는 메타데이터 조회 → 실행 확인 → 다운로드 → 미디어 검사 → 처리 → 결과 검사 → 최종 확정 → 완료로 구분한다. 다운로드와 처리는 각 단계의 진행률을 표시하며 전체 합산 퍼센트는 계산하지 않는다. 진행률을 알 수 없으면 단계 이름과 진행 중을 표시한다. 단계의 100%는 전체 완료를 뜻하지 않는다.

터미널에서는 진행 표시를 같은 줄에서 갱신한다. stderr가 파일 등으로 리디렉션되면 단계 전환만 줄 단위로 기록하고 반복 퍼센트 갱신은 출력하지 않는다. 경고·오류는 어느 경우에도 출력한다. 구체적인 갱신 빈도와 진행 이벤트 모델은 관련 계약 설계에서 정한다.

### 4.16 Application 작업 결과 — 사용자 채택 완료

2026-10-09 사용자가 CLI와 향후 WPF에서 재사용할 다음 최종 결과 계약을 채택했다.

| 결과 | 의미 |
|---|---|
| Succeeded | 검사·최종 파일 확정 완료 |
| Failed | 입력 오류 또는 실행 실패 |
| Cancelled | 사용자 취소 및 프로세스 종료 확인 완료 |

결과는 작업 ID, 최종 상태, 성공한 경우에만 출력 절대경로, 실패 시 오류 코드·안전한 설명, 주의사항 목록, 정리 실패 시 남은 임시 경로 목록을 포함한다. 정확도 제한이나 임시 파일 정리 실패는 주의사항으로 전달한다. 프로세스 종료 확인 실패는 제4.13절에 따라 Failed다.

외부 프로세스 객체·명령 인자·원시 stderr는 공개 결과에 넣지 않고 민감값을 제거한 진단 로그에 남긴다. Application은 CLI 숫자 종료 코드를 알지 않으며 CLI가 성공 0, 입력 오류 2, 실행 실패 1, 취소 130으로 변환한다.

예상 가능한 오류는 결과로 반환하되 프로그래밍 오류까지 모두 잡아서 일반 실패로 숨기지 않는다. 오류 코드·분류는 제4.19절, 필드 타입·Application 시그니처는 제4.30절을 따른다.

### 4.17 진행 이벤트 — 사용자 채택 완료

2026-10-09 사용자가 Application의 진행 정보와 호스트 표시 책임을 분리하는 다음 계약을 채택했다.

| 정보 | 의미 |
|---|---|
| 작업 ID | 어떤 작업의 이벤트인지 식별 |
| 단계 | 메타데이터 조회·다운로드·입력 검사·처리·결과 검사·최종 확정·취소 중 |
| 단계 진행률 | 0~100, 알 수 없으면 값 없음 |
| 안전한 설명 | 현재 수행 중인 작업 안내 |

진행률은 현재 단계 기준이며 단계 변경 시 이전 값을 초기화한다. 다운로드·처리 등 근거가 있는 단계만 퍼센트를 제공한다. 취소 중은 표시 상태이며 취소 완료는 최종 Cancelled 결과로 판단한다. 성공·실패·취소의 최종 판단은 제4.16절 작업 결과 계약만 사용한다.

Y/N 질문·응답 대기는 CLI 책임이며 Application에 콘솔 입력 기능을 넣지 않는다. Application은 이벤트를 전달하고 줄 갱신·출력 빈도·WPF 표시 방식은 호스트가 결정한다. CLI의 출력 위치·리디렉션 동작은 제4.15절을 따른다.

### 4.18 준비·실행 서비스 경계 — 사용자 채택 완료

2026-10-09 사용자가 확인 전 준비와 확인 후 실행을 분리하는 다음 Application 경계를 채택했다.

| 동작 | 책임 |
|---|---|
| 메타데이터 조회 | URL 검증·조회, info에서도 재사용 |
| 클립 준비 | 선택 화질·모드·구간·출력 검증, 확인할 작업 요약 생성 |
| 클립 실행 | 준비 결과를 받아 획득·처리·검사·최종 확정 |

CLI는 메타데이터 조회 → 클립 준비 → 요약 표시 → Y/N 또는 --yes → 클립 실행 순서로 조정한다. 준비 결과는 작업 ID, 소스·선택 포맷, 요청 구간·모드, 출력 절대경로, 주의사항과 미확인 검사 항목을 포함하는 불변 데이터다. 확인 이후 입력값을 다시 읽어 작업 내용을 변경하지 않는다.

준비 단계에서는 구간 획득이나 출력 파일 생성을 하지 않는다. 이때 확인할 수 없는 FPS·코덱·시간축은 미확인으로 표시하고 실행 단계에서 확인한다. 끝내 필수 조건을 충족하지 못하면 실패하며 화질·모드를 자동 변경하지 않는다. 확인 대기 중 파일 충돌 등의 변화가 생길 수 있으므로 실행 시 필요한 검사는 재수행한다. 준비 통과는 실행 성공 보장이 아니다.

FPS 미확인 준비 결과에는 FPS 기반 계산이 완료된 구간 대신 요청한 시간코드 성분을 보존해야 한다. 불변 준비 결과와 검증을 완료한 실행 작업의 구체적인 타입·시그니처는 후속 모델 설계에서 구분한다.

| 오류 코드 | 의미 |
|---|---|
| InvalidInput | 옵션·타임코드 문법 등 잘못된 입력 |
| UnsupportedSource | 지원하지 않는 URL |
| InvalidRange | 프레임 범위·IN/OUT·영상 길이 위반 |

### 4.20 시간 모델 — 사용자 채택 완료

2026-10-10 사용자가 FPS 미확인 입력과 검증된 시간을 구분하는 다음 Media.Core 모델 구조를 채택했다.

| 모델 | 정보·책임 |
|---|---|
| TimecodeInput | HH·MM·SS·FF 성분, FPS 없이 입력 보존 |
| FrameRate | 양의 분자·분모, 약분한 유리수 FPS |
| Timecode | 검증된 입력 성분과 확정 FPS, 시간·프레임 변환 |
| MediaTimeRange | 검증된 시작·종료 시간, [Start, End) 구간 |

모든 모델은 생성 후 불변이다. TimecodeInput은 문법 검사를 통과한 입력이며 실행 가능한 시간이라는 보장은 없다. Timecode는 분·초·프레임 범위 검증까지 통과해야 생성한다. MediaTimeRange는 같은 FPS의 시작·종료로 생성하며 Start >= 0과 End > Start를 보장한다. End <= 영상 길이는 영상 정보를 아는 Application에서 추가 검사한다.

정확한 값으로 계산·비교하고 TimeSpan으로 전달하는 경계에서만 제4.1절 tick 반올림을 적용한다. FPS가 바뀌면 기존 Timecode를 수정하지 않고 입력 성분으로 재검증한다. nullable FPS를 가진 하나의 타임코드 타입 대신 입력과 검증 완료 값을 분리한다. 숫자 필드의 구체적인 CLR 타입·overflow 처리 구현은 이 범위와 정확도 정책을 유지하도록 상세 구현 계획에서 명시한다.

### 4.21 다운로더 메타데이터 모델 — 사용자 채택 완료

2026-10-10 사용자가 포맷별 FPS를 계산 기준으로 사용하는 이유를 검토한 뒤 다음 Downloader.Application 모델 구조를 채택했다.

| 모델 | 주요 필드 |
|---|---|
| VideoSourceReference | 플랫폼, 영상 ID, 정규화된 페이지 URL |
| VideoInfo | 소스, 제목, 길이, 업로더, 썸네일 URL, 업로드 날짜, 영상 상태, 포맷 목록 |
| VideoFormat | 포맷 ID, 가로·세로 해상도, FPS, 영상·음성 코덱, 영상·음성 스트림 유무 |

모델과 포맷 목록은 조회 시점의 불변 데이터다. 누락 가능한 필드는 값 없음으로 보존하고 제목 없음 등의 표시 문구는 호스트에서 생성한다. FPS는 포맷별로 보존하며 VideoInfo에 영상 전체를 대표하는 단일 FPS를 저장하지 않는다. 타임코드 계산은 실제 선택한 영상 포맷의 FPS를 사용한다. 화면에 대표값을 표시하는 경우에도 그 의미를 명시하며 계산 기준과 혼동하지 않는다.

스트림 유무는 있음/없음/미확인을 구분한다. 코덱 정보 누락을 스트림 없음으로 단정하지 않는다. 영상 상태는 완료 영상/라이브/예정/미확인으로 구분하여 실행 적합성 검사에 사용한다. 원시 yt-dlp JSON, 인증정보, 서명된 스트림 URL은 공개 모델에 포함하지 않으며 실행용 스트림 정보는 Infrastructure 내부에서 관리한다.

화질 요청과 실제 video/audio 조합은 별도의 포맷 선택 모델에서 정의한다. 포맷별 FPS가 달라질 수 있다는 공식 근거는 [yt-dlp 포맷 정렬](https://github.com/yt-dlp/yt-dlp#sorting-formats)을 참조한다. 제공받은 실제 영상의 FPS·포맷 목록은 아직 확인하지 않았다.

### 4.22 화질 요청·포맷 선택 — 사용자 채택 완료

2026-10-10 사용자가 사용자 요청과 실제 선택 결과를 분리하는 다음 Downloader.Application 모델을 채택했다.

| 모델 | 정보 |
|---|---|
| QualityOption | Best 또는 지정 해상도(예: 720p) |
| FormatSelection | 선택한 영상 포맷, 필요하면 별도 음성 포맷, 선택 이유·주의사항 |

720p는 높이 720인 실제 제공 포맷에서 선택하며 없으면 오류다. 다른 해상도로 자동 변경하지 않는다. 영상·음성이 함께 있는 포맷은 별도 음성 포맷 없이 표현하고 영상 전용 포맷이면 필요한 음성 포맷을 함께 선택한다. 원본에 음성이 없으면 무음 선택을 허용하되 음성 유무 미확인을 무음으로 단정하지 않는다.

FPS는 선택한 영상 포맷에서 가져오며 FormatSelection에 중복 저장하지 않는다. 선택 결과는 불변이며 확인 화면에 실제 해상도·FPS·코덱·음성 유무를 표시한다. Best 정렬 우선순위와 모드별 코덱 호환성은 실험 후 결정 항목으로 유지한다.

후속 구현: [3c-1 계약 결과](PHASE_1_STAGE_3C1_RESULT.md). 후보 조합의 snapshot·높이·A/V 불변 조건을 구현했다. 자동 순위는 구현하지 않았으며 [잔여 실험 계획](PHASE_1_STAGE_3C_EXPERIMENT_PLAN.md)의 실제 근거를 확보한 뒤 다음 단위로 진행한다.

3c-2 후속: [실제 실험·선택 결과](PHASE_1_STAGE_3C2_RESULT.md)에 metadata 선언값의 순위와 codec/transport 동률 정책을 기록했다. Best는 높이·유리수 FPS·폭을 먼저 비교하며 codec/transport 때문에 낮은 해상도로 자동 변경하지 않는다. 모드별 Fast 허용 조합·Accurate 정확도는 실제 획득/시간축 실패를 보완한 뒤 확정한다. 위 3c-1 미구현 문구는 당시 기록이다.

후속 [CHZZK 로그 진단](PHASE_1_CHZZK_HLS_DIAGNOSIS.md): 같은 hls-3192/[90,100)초 요청 한 번의 안전한 오류 로그와 FFmpeg 8.1 소스를 대조해 HLS 확장자/감지 형식 일치 검사에서의 거부를 확인했다. 입력 옵션 대조·수정·1080p/시간축 성공 검증은 아직 수행하지 않았다.

추가 [CHZZK 옵션 대조](PHASE_1_CHZZK_HLS_COMPARISON.md): extension_picky 0을 FFmpeg 입력별로 전달해 같은 구간의 720p·1080p 획득/probe/decode를 확인했다. 720p 끝의 PTS 간격 점프·1080p의 약 1.007초 A/V 시작 차이를 관찰했다. 옵션은 실험에만 적용했으며 전역 제품 정책·정밀 구간/CFR/동기·전체 Phase 완료로 확정하지 않았다. 위 미수행 문구는 초기 진단 시점이다.

2026-10-11 [CHZZK 음성 coverage 진단](PHASE_1_CHZZK_AV_TIMING_DIAGNOSIS.md): 1080p 영상 600·음성 422 packet의 source payload/PTS 대응을 확인했다. 요청 시작 근처의 원본 음성 packet 47개는 획득 파일에 없으며 edit list를 제거해 해결할 문제가 아니다. 여유 구간 획득·공통 source/local origin·정밀 구간/음성 sample 처리의 대조를 다음 단위로 남긴다.

후속 [CHZZK 여유 획득·trim](PHASE_1_CHZZK_PREROLL_TRIM_EXPERIMENT.md): 47개 누락 packet·IN overlap을 확보하고 같은 source target clock으로 영상 PTS 600개·선택 PCM 및 AAC 유효 sample 수를 대조했다. 영상·음성의 local offset을 각자 STARTPTS로 없애지 않았다. source sample gap/overlap·padding·표시 종료와 일반화 검증은 남아 있어 4단계 제품 계약·전체 정확도/Phase 완료는 아직 확정하지 않는다.

추가 [CHZZK IN/포맷 확대](PHASE_1_CHZZK_GENERALIZATION_EXPERIMENT.md): 두 포맷의 fractional IN에서 target coverage/후보 trim을 재현했지만, 동일 source audio payload의 raw PTS는 거의 같은데 stream minimum 후보가 64ms 달라짐을 확인했다. 화질과 독립적인 source 원점 근거가 필요하며 header start/임의 고정 2초를 원본 시간 0으로 채택하지 않는다.

2026-10-11 해석 정리: 현재 요구사항은 품질 독립 원점이나 임의 browser 세션 시간의 정확한 재현을 명시하지 않는다. 앞선 공통 원점 실험은 추가 보증의 가능성을 조사한 기록이며 선택 포맷 상대 시간 정의 자체를 배제하는 근거는 아니다. [source 시간 하위 계약안](PHASE_1_SOURCE_TIMELINE_CONTRACT_DRAFT.md)에 선택 포맷 기준 권고·추가 보증 대안·mapping gate를 정리했다. 후속 사용자 지시로 원점 의미 A(선택 포맷 기준)를 채택했다. 구체 측정·mapping·오류 확장안의 검증/통합과 기존 일반 정책은 별도로 유지한다.

### 4.23 준비 결과·실행 작업 모델 — 사용자 채택 완료

2026-10-10 사용자가 확인 화면의 정보와 검증된 실행 데이터를 구분하는 다음 Downloader.Application 모델을 채택했다.

| 모델 | 정보 |
|---|---|
| ClipRequest | 소스 URL, IN/OUT 입력 성분, 요청 화질·모드, 출력 절대경로 |
| PreparedClip | 작업 ID, 요청, 조회한 영상 정보, 포맷 선택 결과, 주의사항·미확인 검사 항목 |
| ClipJob | 작업 ID, 소스, 선택 포맷, 검증된 시간 구간·FPS, 모드, 출력 절대경로 |

모두 불변 데이터다. CLI는 PreparedClip으로 확인 화면을 만들고 확인받은 동일한 준비 결과를 실행에 전달한다. 실행 중 미확인 FPS 등을 확인하고 시간·영상 길이 검증을 마친 뒤 ClipJob을 생성한다. ClipJob에는 FPS나 구간이 미확인인 상태를 허용하지 않는다.

준비 때의 정보와 실행 때 확인한 정보가 다르면 재검증하며 요청한 화질·모드·IN/OUT은 자동 변경하지 않는다. 임시 파일 경로와 프로세스 상태는 별도 실행 자원으로 관리하고 작업 모델에 넣지 않는다. FPS 확인 방법·시점은 실험에서 결정하며 준비 완료와 실행 조건 검증 완료를 구분한다.

### 4.24 ProcessRunner — 사용자 채택 완료

2026-10-10 사용자가 외부 프로그램 실행만 담당하는 다음 Media.Infrastructure 계약을 채택했다. 사이트·코덱·JSON 해석은 도구별 어댑터 책임이다.

| 모델 | 주요 정보 |
|---|---|
| ProcessRequest | 실행 파일 절대경로, 개별 인자 목록, 작업 디렉터리, 타임아웃, stdout/stderr 수집 정책 |
| ProcessResult | 실행 상태, 종료 코드, 수집한 출력, 출력 생략 여부, 실패 사유 |

| 실행 상태 | 의미 |
|---|---|
| Exited | 프로세스 정상 종료, 종료 코드는 별도 확인 |
| StartFailed | 프로세스 시작 실패 |
| Cancelled | 취소 및 종료 확인 완료 |
| TimedOut | 시간 초과 및 종료 확인 완료 |
| ExecutionFailed | 출력 읽기 등 실행 관리 실패 |
| TerminationFailed | 종료 확인 실패 |

종료 코드가 0이 아니어도 Exited이며 의미는 도구 어댑터가 해석한다. 취소 토큰과 출력 수신 함수는 실행 호출에 전달하고 불변 작업 모델에는 저장하지 않는다. 출력 수신 함수는 진행률 해석에 사용하며 ProcessRunner는 도구별 진행률 형식을 알지 않는다.

수집 상한·타임아웃·종료 정리는 제4.11~4.13절의 정책을 적용한다. 원시 출력은 Infrastructure 내부 결과에만 보존하고 공개 Application 결과에는 노출하지 않는다. 종료 코드 등 종료 정보를 확보하지 못한 경우 값 없음을 허용하되 임의의 성공 코드로 대체하지 않는다.

### 4.25 획득 결과·공유 미디어 입력 경계 — 사용자 채택 완료

2026-10-10 사용자가 사이트별 획득 결과와 공유 미디어 처리를 분리하는 다음 모델 경계를 채택했다.

| 모델 | 위치·정보 |
|---|---|
| AcquiredMedia | Downloader.Application: 획득 파일, 요청 구간, 확인된 원본/로컬 시간축 관계, 검사 결과·제한 |
| MediaInput | Media.Core: 로컬 미디어 파일과 확인된 스트림·시간축 정보 |
| MediaProcessingRequest | Media.Core: 입력, 로컬 입력 기준 추출 범위, 모드, staging 출력 경로 |

공유 미디어 계층에는 플랫폼·페이지 URL·yt-dlp 포맷 ID·인증정보를 전달하지 않는다. 영상·음성이 분리된 파일로 획득되면 MediaInput에서 표현한다. Application이 원본 IN/OUT과 확인된 시간축 관계를 사용해 로컬 추출 범위를 계산한다. 요청한 시작 시간이 임시 파일의 0초라는 가정은 사용하지 않는다.

시간축 관계가 미확인이면 그 상태를 보존하며 Accurate에 필요한 근거가 없으면 진행하지 않는다. 공유 처리는 staging 생성까지 담당하고 최종 이름 확정은 출력 작업 공간 책임이다. 시간축 관계의 구체적인 표현·로컬 범위 타입·변환 방법은 실험 후 결정한다.

### 4.26 공유 미디어 검사·처리 서비스 — 사용자 채택 완료

2026-10-10 사용자가 다음 Media.Core 계약과 책임 경계를 채택했다. 구현은 Media.Infrastructure에 둔다.

| 계약 | 책임·반환 정보 |
|---|---|
| IMediaProbe | 파일 검사 → 길이·스트림·코덱·FPS·타임스탬프·검사 제한 반환 |
| IMediaProcessingService | trim·mux·remux·재인코딩 → staging 경로·실제 처리 내용·제한 반환 |

두 서비스 모두 비동기 호출과 취소 토큰을 지원한다. IMediaProbe는 측정 결과를 반환하며 확장자나 파일 존재만으로 성공을 판단하지 않는다. Application이 측정 결과를 요청 구간·음성 요구·모드별 조건과 비교한다. 기본 검사는 미디어 정보 중심으로 수행하며 필요한 경우에만 프레임 타임스탬프를 검사한다.

이미 수행했고 요구사항을 충족한 trim/mux는 반복하지 않는다. 처리 서비스 성공은 staging 생성 완료이며 결과 검사와 최종 파일 확정을 마쳐야 전체 작업 성공이다. 공유 서비스는 Downloader 오류 타입에 의존하지 않으며 미디어 오류는 Downloader 경계에서 채택한 Application 오류 코드로 변환한다.

정확도 허용 오차와 타임스탬프 검사 범위는 실험 후 확정한다.

### 4.27 출력 작업 공간 계약 — 사용자 채택 완료

2026-10-10 사용자가 IOutputWorkspace가 작업 공간을 생성하고 작업별 세션이 파일 수명을 관리하는 다음 계약을 채택했다.

| 동작 | 책임 |
|---|---|
| 작업 공간 생성 | 출력 경로 재검사, 작업 폴더·고유 staging 경로 준비 |
| 최종 확정 | 검사를 마친 staging을 최종 경로로 이동 |
| 정리 | 해당 작업이 생성한 임시 파일 제거, 실패·잔존 경로 반환 |

세션에는 작업 ID, 임시 폴더, staging 경로, 최종 출력 경로를 보존한다. 작업 공간은 Y 또는 --yes 이후 생성한다. Application이 미디어 결과 검사 통과를 확인한 뒤 최종 확정을 호출하며 작업 공간은 정확도를 판단하지 않는다.

최종 확정은 한 번만 허용하고 이동 순간에도 기존 파일을 덮어쓰지 않는다. 작업 공간 생성은 최종 파일명 예약을 보장하지 않으므로 다른 작업이 먼저 생성하면 충돌로 실패한다. 성공 후 정리에서도 확정된 최종 파일은 삭제하지 않는다.

정리는 명시적으로 수행하고 결과를 확인하며 자동 자원 해제에만 의존하여 정리 실패를 숨기지 않는다. 프로세스 종료가 확인되지 않으면 사용 중일 수 있는 파일은 보존하고 안내한다.

### 4.28 도구 실행 전 진단 — 사용자 채택 완료

2026-10-10 사용자가 명령에 필요한 도구만 검사하는 다음 정책을 채택했다.

| 명령 | 검사 범위 |
|---|---|
| diagnose | yt-dlp·FFmpeg·ffprobe의 경로·실행·버전 |
| info | yt-dlp의 경로·실행·버전 |
| clip | 세 도구 모두 검사, 선택 모드에 필요한 기능 추가 확인 |

clip 기본 도구 검사는 Y/N 확인 전 수행한다. Accurate에 필요한 인코더 등은 처리 전략 확정 후 검사 항목에 연결한다. 경로 발견, 실행 성공, 버전 확인, 필요한 기능 지원은 구분하여 표시한다.

검사 결과는 현재 명령 실행 동안만 재사용하며 다음 실행에서는 다시 확인한다. 검사 후 삭제·변경 등 실제 실행 실패도 처리하고 다른 경로로 자동 대체하지 않는다. diagnose는 한 도구가 실패해도 나머지를 검사하며 모두 통과하면 0, 필요한 도구 검사 실패가 있으면 1을 반환한다.

기존 WPF 파일 존재 진단은 유지하며 Found의 의미를 실행·버전 검증으로 변경하지 않는다. 버전 확인 성공은 사이트 접근 성공 보장이 아니다. YouTube JS 의존성은 실험 결과로 진단 범위를 보완한다.

### 4.29 재시도·스트림 정보 갱신 — 사용자 채택 완료

2026-10-10 사용자가 Application 전체 작업 재시도와 도구 내부 재시도를 분리하는 다음 정책을 채택했다.

| 상황 | 처리 |
|---|---|
| Application 조회·다운로드·처리 실패 | 전체 작업 자동 재시도 없음 |
| yt-dlp 내부 네트워크·extractor·fragment 오류 | 해당 재시도 단위마다 최대 2회 추가 시도 |
| 파일 접근 오류 | 자동 재시도 없음 |
| 취소·타임아웃·검사 실패 | 자동 재시도 없음 |
| fragment 획득 불가 | 누락 구간을 건너뛰지 않고 실패 |

서명된 스트림 URL은 확인 화면의 영구 데이터로 저장하지 않고 실행할 때 확보한다. 이는 실패 후 재시도가 아닌 정상 실행 단계다. 동일 영상·선택 포맷인지 다시 확인하고 포맷이 사라졌거나 실행 조건이 달라지면 실패한다. 만료·접근 오류가 나도 다른 화질·모드로 자동 변경하지 않는다.

사용자가 명령을 다시 실행하면 새 작업 ID로 시작한다. 메타데이터 조회 내부 재시도도 기존 120초 제한에 포함한다. 2회는 초기 내부 정책값이며 실제 사이트 검증에서 조정할 수 있다. [yt-dlp 공식 옵션](https://github.com/yt-dlp/yt-dlp#download-options)을 기준으로 재시도·fragment 누락 정책을 명시하며 기본값에만 의존하지 않는다. 외부 FFmpeg 등 실제 획득 경로가 달라지는 경우 재시도 적용 가능 범위는 실험에서 확인한다.

### 4.30 필드 타입·Application API — 사용자 채택 완료

2026-10-10 사용자가 다음 모델 타입과 Application 호출 계약을 채택했다.

| 정보 | 타입 |
|---|---|
| 작업 ID | Guid |
| 페이지·썸네일 URL | Uri / Uri? |
| 제목·업로더·코덱 등 누락 가능 정보 | string? |
| 영상 길이 | TimeSpan? |
| 업로드 날짜 | DateOnly? |
| 해상도 | int? |

| 단계 진행률 | double? |
| 상태·모드·오류 코드 | 각각의 enum |

목록은 생성 시 복사하고 외부 변경을 차단한다. 시간 계산에는 정확한 정수·유리수 연산을 사용하고 중간 overflow를 방지한다. 표현 범위를 넘으면 명시적으로 실패시킨다.

| 서비스·메서드 | 입력 | 반환 |
|---|---|---|
| IVideoInfoService.GetVideoInfoAsync | Uri url, CancellationToken cancellationToken | `Task<OperationResult<VideoInfo>>` |
| IClipJobService.PrepareAsync | ClipRequest request, VideoInfo videoInfo, CancellationToken cancellationToken | `Task<OperationResult<PreparedClip>>` |
| IClipJobService.ExecuteAsync | PreparedClip preparedClip, `IProgress<JobProgress>?` progress, CancellationToken cancellationToken | `Task<ClipJobResult>` |

OperationResult<T>는 조회·준비의 성공 데이터, 오류 또는 취소를 표현하며 실행은 제4.16절 ClipJobResult를 사용한다. PrepareAsync는 요청 URL과 메타데이터 소스의 일치를 검사한다. 실행 API에는 콘솔 입력이나 --yes를 전달하지 않는다. 예상 가능한 실패·취소는 결과로 반환한다.

시간축 관계·로컬 추출 범위의 구체 타입은 실험 후 확정한다. Infrastructure·공유 미디어 계약의 최종 시그니처와 실패 타입 매핑은 이 계층 경계를 유지하도록 통합 검토에서 정리한다.

## 5. 상세 책임·계약과 데이터 흐름

CLI 입력 → 도구 진단·Application 메타데이터 조회 → 포맷 선택·사전 검증 → PreparedClip → 요약 표시·Y/N 또는 --yes → 실행 조건 재확인 → 필요 시 FPS 추가 확인·ClipJob 생성 → 작업 공간·원격 획득 → 시간축·입력 검사 → 공유 미디어 처리 → 결과 검사 → 최종 파일 확정 → 임시 파일 정리·결과 반환.

FPS 추가 확인과 구간 획득의 구체적인 선후 관계는 실험에서 결정한다. 작업 공간의 쓰기는 사용자 확인 이후에만 수행한다. 미확인 FPS를 가진 PreparedClip을 검증된 ClipJob으로 취급하지 않는다.

공유 Processor는 다운로더 ClipJob이나 플랫폼 URL 모델 대신 MediaInput과 시간 범위를 받는다. 프로세스 타입·인자는 Application 및 호스트로 노출하지 않는다. 다운로드와 처리 진행률을 구분하고 알 수 없는 값은 불확정으로 표시한다.

채택된 모델·Application API·상태·결과 계약은 제4.16~4.30절을 따른다. 하위 서비스의 최종 시그니처와 실패 매핑, 파일별 변경 목록은 통합 정리 대상이며 시간축 관련 타입은 실험 의존이다.

### 5.1 통합 검토 기록

2026-10-10 문서 검토에서 다음 연결 조건을 확인했다. 이는 구현·실제 동작 검증 결과가 아니다.

- Y/N 확인은 CLI 책임, PreparedClip/ClipJob과 실행 결과는 Application 책임, ProcessRunner는 Infrastructure 책임이다.
- 기본 종료 코드는 0/1/2/130이다. 취소 중 종료 확인 실패는 1, 성공한 최종 확정 뒤의 취소는 0이며 단순 파일 정리 경고는 원래 결과를 덮지 않는다.
- 진단의 Found, 실행 가능, 미디어 검사 통과, 최종 결과 성공은 서로 다른 확인 수준이다.
- 조회·준비에는 출력 생성이 없으며 출력 작업 공간과 구간 획득은 확인 이후 시작한다. FPS 미확인 때문에 실행 중 사전 확인이 필요한 경우도 미확인 상태를 사용자에게 표시한다.
- 초기 CLI의 필수 --output은 유지한다. 제목 누락 시 ID를 이용한 자동 파일명 정책은 향후 자동 이름 생성 연결용이며 현재 CLI에 자동 이름 옵션을 추가한 결정이 아니다.
- 메타데이터 숫자의 저장 범위, JSON 바이트 상한·디코딩, 미디어/프로세스 실패 타입의 Application 매핑은 구현 전 계약 표로 구체화한다. 이 항목들은 새 제품 기능이나 별도 사용자 정책 제안을 뜻하지 않는다.
- 확인 후 스트림 재조회에서 선택 FPS 등 입력 의미가 달라질 수 있는 경우를 실제 포맷 실험에 포함한다. 변경 정보를 조용히 동일한 실행 조건으로 간주하지 않는다.

## 6. 실험으로 남기는 사항과 해결 시점

실행 전 계약·절차 구체화는 [하위 계약 통합·파일 변경 계획](PHASE_1_CONTRACT_INTEGRATION.md), [최소 실험 실행 절차](PHASE_1_EXPERIMENT_RUNBOOK.md)에 연결한다. 이 보충 자료는 채택 정책을 유지한 구현 방안과 실행 전 기준이며 실험 의존 타입·전략의 확정 또는 실험 성공 기록이 아니다.

| 항목 | 필요한 증거 | 해결 시점 / 차단 범위 |
|---|---|---|
| 획득 시간축 | 알려진 타임스탬프·프레임이 있는 로컬 기준 영상과 사이트 구간의 원본/획득 결과 대조 | 추출 알고리즘 확정 전; Accurate 구현 경로 차단 |
| CFR/VFR·FPS | 실제 선택 포맷·ffprobe 프레임 PTS, 소수 FPS와 VFR 결과 | FPS fallback·Accurate 성공 정책 확정 전 |
| 코덱·인코더 | 사용 FFmpeg의 지원 기능과 실제 짧은 출력 | Best 정렬·모드별 처리 계획 확정 전 |
| YouTube 의존성 | 설치 yt-dlp 버전·EJS·JS runtime·실제 조회 | 사이트 완료 검증 전 |
