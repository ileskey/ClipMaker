작성일: 2026-10-10 (Asia/Seoul).

상태: **문서·소스 점검 완료, 실험 계획 초안**. 일반 정책은 이미 채택됐으며 재승인 대상이 아니다. 아래 실험 판정 방법과 하위 계약 구체화는 검토할 계획이고, 실험 결과·전체 설계 확정·구현 완료가 아니다.

- Phase 0 빌드·22개 테스트·WPF 수명 검증은 기존 결과 기록으로 확인했다. 이번에 재수행하지 않았다.

전체 구조의 초기 소스 설명, 체크리스트의 URL 미제공·일반 정책 미정 문구, Phase 0 검증 당시의 미커밋 표현은 과거 기록이다. 최신 상세 설계·완료 인계·현재 Git 관찰을 우선한다. 이 점검으로 과거 문서를 다시 쓰거나 요구사항을 바꾸지 않는다.

## 3. 하위 계약 통합 목록

| 영역 | 구현 전에 명시할 내용 | 실험 의존 부분 |
|---|---|---|
| 시간·숫자 | 채택한 long/int 필드, 정확한 중간 연산, tick 경계, decimal JSON의 유리수 변환·범위 초과, Duration 변환, 실패 반환 | 실제 FPS 표현 샘플 |
| ProcessRunner | RunAsync 입력/반환·수신 함수, 스트림별 수집 정책, 원시 바이트 상한과 디코더 경계, 긴 단일 행, callback 실패, 종료 코드 nullable, 중단 원인 우선순위 | root/자식/파이프 종료 확인 수단 |
| 실행 진단 | 기존 파일 진단과 분리한 실행·버전·기능 결과, 명령별 필수 도구, 15초 제한·명시 경로 재사용 | JS runtime·EJS·인코더 항목 |
| 소스·획득 | URL ID 문법·Uri 경계 사례, JSON 변환, 선택 포맷 유지·실행 재조회, 획득 요청/결과·자원 소유권 | Best 순위·Fast 조합·시간축 근거 |
| 미디어 | Probe/Process 비동기 시그니처·공유 실패 타입·분리 A/V 파일·PTS 단위·시간 기준 | 원본↔로컬 변환·CFR 판정·Accurate 제한 |
| 출력 세션 | 생성/확정/정리 결과·한 번만 확정·충돌·생성 파일 추적·종료 미확인 보존 | 필수 실험 의존 없음 |
| Application | 하위 실패→채택 오류 코드/입력·실행 분류, 준비→실행 재검사, 최종 확정/취소 동기화, 결과·주의사항 분리 | FPS 추가 확인·획득·ClipJob 생성 순서 |

핵심 연결 문제: FPS가 없는 준비 결과는 TimecodeInput을 보존해야 한다. ClipJob 생성에는 확정 FPS가 필요하므로 획득을 ClipJob에만 의존시키면 순환할 수 있다. 원격 probe가 가능한지, 확인 이후의 별도 최소 검사로 해결 가능한지 실험한다. 확인 전 구간 획득·출력 생성 금지, 임의 FPS 금지, 필수 검증 우회 금지는 그대로 유지한다. 이 문제를 추정 FPS나 전체 다운로드로 해결하지 않는다.

실패 매핑 표에는 최소 StartFailed/ExecutionFailed/Exited(nonzero) → ProcessFailed, TimedOut → TimedOut, TerminationFailed → ProcessTerminationFailed, 종료 확인된 취소 → Cancelled를 연결한다. JSON 상한·파싱 실패는 조회 경계의 InvalidMetadata, 미디어 조건 불일치는 VerificationFailed, 출력 쓰기/확정 실패는 OutputFailed로 구분하는 초안을 검토한다. 출력 충돌의 입력/실행 분류는 발견 시점에 따른 기존 정책을 유지한다.

파일 계획은 Media.Core의 ValueObjects/Models/Contracts, Media.Infrastructure의 ProcessExecution/Tools/FFprobe/FFmpeg, Downloader.Application의 Models/Contracts/Validation/UseCases, Downloader.Infrastructure의 Sources/YtDlp/Downloads/FileSystem과 관련 테스트로 작성한다. CLI·솔루션 등록은 6단계에서 한다. 지금 폴더·빈 파일·프로젝트를 만들지 않는다.

## 4. 최소 실험 계획

공통 기록: 질문, 기준 commit, OS/SDK, 실행 파일 경로·버전, 인자(민감값 제거), 입력/선택 포맷, 저장 위치, 요청·실제 구간, stdout/stderr 요약·종료 코드, 관찰, 판정, 제한, 설계 영향. 실행 전 새 run ID로 위치를 격리한다. 계획한 실험 루트는 저장소의 `.phase1-experiments/<run-id>/`이며 아직 만들지 않았다. 실제 사이트 결과는 공개 fixture로 복제하지 않고 익명화한 최소 필드만 추후 채택한다. 임시 결과는 기존 사용자 파일과 혼합하지 않는다.

### E0 — 도구·기능·의존성

- 질문: 현재 준비된 도구로 조회·구간 획득·MP4 copy/encode를 수행할 수 있는가?
- 범위: 실제 경로·버전, FFmpeg 인코더/컨테이너, yt-dlp 버전별 공식 의존성·재시도 옵션·JS/EJS 구성 확인. 도구가 없으면 설치를 자동 수행하지 않고 미충족으로 기록한다.
- 판정: 파일 발견/실행/버전/기능을 각각 기록한다. 현재 설치 버전의 공식 자료와 실행 결과가 함께 있어야 최소 실행 구성을 확정한다. node 발견만으로 YouTube 지원을 인정하지 않는다. JS 실행 경로·자동 원격 구성요소 비사용 조건·옵션은 확인 후 결정한다.

### E1 — 로컬 시간축·seek/copy/encode

- 입력: 프레임 식별 표시·알려진 PTS·오디오 기준 신호를 가진 짧은 CFR(정수 및 30000/1001), VFR 기준 영상. keyframe과 일치하지 않는 IN/OUT을 포함한다. 제품 프로젝트와 분리된 검증 입력이다.
- 범위: 짧은 동일 구간의 copy와 전체 구간 encode를 비교한다. 원본·획득/처리 결과의 첫/끝 표시 프레임, packet/frame PTS, time_base, start_time, A/V 기준 신호를 대조한다. PTS를 0으로 재설정한 사례도 포함한다.
- 사전 판정 제안: Accurate 영상은 원본 PTS가 [Start, End)에 속하는 프레임 집합을 기준으로 첫/끝 프레임·개수를 대조한다. 프레임 식별 표시로 대응을 확인하고 재인코딩 픽셀 동일성은 요구하지 않는다. 출력의 시간 이동을 하나의 기준으로 설명할 수 있어야 한다.
- 음성: codec priming/padding·출력 sample rate·검사 분해능을 먼저 식별해 측정 한계를 기록한다. 기준 신호로 A/V offset과 drift를 측정한다. 그 한계에 근거한 허용 범위를 실행 전에 기록하며 임의 ms/몇 프레임을 사후 통과 기준으로 만들지 않는다. 아직 수치 허용 오차는 확정하지 않았다.
- Fast는 실제 원본 위치·키프레임·시작/끝 편차·음성 유지를 기록한다. Accurate의 기준을 적용해 Fast를 판정하거나 ‘몇 프레임’ 이내라고 보장하지 않는다. 영상/음성 누락·재생 불가·요청과 무관한 구간은 허용하지 않는다.
- 산출물: 확인 가능한 원본↔로컬 변환 근거, 모드별 검사 범위·제한. 단순 start_time=0, 평균 FPS 일치만으로 시간축·CFR을 인정하지 않는다.

### E2 — 사이트 메타데이터·짧은 구간 획득

- 입력: CHZZK `https://chzzk.naver.com/video/15430558`, YouTube `https://www.youtube.com/watch?v=sFXPM_sfJNo`. 접근·완료 상태·길이를 조회한 뒤 각 10~30초 구간을 정한다. 현재 시작/종료값을 지어내지 않는다.
- 먼저 metadata-only 조회로 실제 video/audio 포맷·FPS·코덱·길이·누락 필드와 의존성을 확인한다. 확인 후 선택한 동일 포맷을 유지해 구간 획득 후보를 최소 1회씩 조사한다.
- `--download-sections` 후보의 실제 위임 명령·PTS·trim/mux 여부·원본 첫 프레임 대응을 관찰한다. 원본 비교는 필요한 작은 겹침 구간·프레임 식별 등으로 한정한다. 대응 증거를 확보하지 못하면 시간축 미확인으로 남긴다.
- FPS 누락 시 원격 검사 가능 여부·검사 비용·순서, 실행 재조회 시 선택 FPS 변화, 분리 A/V·실제 fragment 재시도 적용 범위를 확인한다. 목록 정렬만으로 Best 실행 전략을 확정하지 않는다.
- 판정: 단일 완료 영상·선택 포맷 유지·영상/음성·재생을 확인한다. Accurate는 E1에서 정한 근거 수준을 사이트에서도 확보해야 한다. 근거가 없으면 Accurate 경로를 차단하고 대안과 계층 영향을 비교한다. 전체 다운로드·다른 화질/모드 fallback은 하지 않는다.
- 접근/의존성 문제로 실행할 수 없으면 원인을 기록한다. 제공 URL이나 메타데이터 성공은 클립 검증 성공을 뜻하지 않는다.

### E3 — 프로세스·자식·파이프 취소

- 입력: 실행별 PID를 추적하는 격리된 검증 프로세스. stdout/stderr 동시 대량 출력, UTF-8 문자 경계·긴 행, JSON 상한 초과, 비정상 종료, 무출력 대기, 파이프를 보유한 자식·root 선종료 사례를 포함한다.
- 범위: 취소/타임아웃/출력 초과 후 root·시작된 자식의 생존, 양 스트림 EOF 또는 읽기 정리, 종료 정보, 부분 파일을 관찰한다. 기존 프로세스를 종료하지 않는다.
- 판정: 교착 없이 동시 drain·상한 유지, 채택한 실행 상태/종료 코드 분리, 별도 10초 정리 범위 내 종료 증거가 필요하다. root 종료만 확인했거나 자식·파이프가 남으면 정상 취소로 판정하지 않는다. 정리 시간 초과는 TerminationFailed 및 사용 가능성 있는 파일 보존이다.
- tree kill로 재현 문제가 해결되지 않으면 Job Object 등 최소 보완을 비교한다. 네이티브 수명 관리 선행 도입은 실험 실패 근거가 있을 때 검토한다. 실제 ProcessRunner의 같은 사례 재검증은 구현 2단계에서 수행한다.

## 5. 후속 구현 운영

실험·계약 통합·설계 반영 후 구현 요청을 받으면 다음 **한 단계씩** 진행한다. 각 단계 안에서도 한 책임과 관련 검증을 묶은 논리적 커밋 단위로 끊어 결과를 보고한다. 실제 Git commit 실행과 commit 수 확정은 별도 지시를 따른다.

1. 시간 모델·입력 검증 — FPS/타임코드, 구간 검증 묶음; 파싱·소수 FPS·정확한 비교·반올림·overflow.
2. ProcessRunner·도구 진단 — 출력/실행, 취소/타임아웃, 실행 진단 묶음; 동시 출력·상한·실패·자식 취소.
3. URL·메타데이터·포맷 — URL, JSON 변환, 포맷 선택 묶음; 정규화·fixture·누락/비정상 필드.
4. 획득·미디어 검사·처리 — 획득, 검사, 처리 묶음; 확인된 시간축·스트림·모드별 결과.
5. 작업 공간·Application — 파일 수명/확정, 준비, 실행 조정 묶음; 실패·취소·충돌·확정 경합.
6. CLI·통합 — 호스트/명령, 확인/진행/취소, 통합 결과 묶음; 종료 코드·Y/N·EOF·--yes·로그·수명.

묶음별 관련 빌드·테스트 통과와 단계 완료를 구분한다. 단계 완료는 해당 도구 통합 검증과 결과 기록까지 포함한다. 마지막에는 솔루션 빌드·기존 탐색 테스트·WPF 회귀·양 사이트 필수 검증을 수행한다. 필수 사이트 검증이 남으면 Phase 1 Completion/tag를 확정하지 않는다. Phase 2·WPF 다운로드 UI·ClipEditor는 범위 밖이다.

이번 실제 수행: 문서 읽기, Git·프로젝트·계약·명령 경로 탐색, 계획 문서 작성. 빌드·테스트·도구 버전 실행·실험·프로젝트 생성·패키지/도구 설치·영상 다운로드·Git 상태 변경 작업은 수행하지 않았다.

`git diff --check`는 종료 코드 0이며 기존 PHASE_DESIGN.md의 LF→CRLF 안내만 있었다. 설치 확인과 기능 목록 조회는 로컬 미디어 실험 또는 제품 구현 검증을 대신하지 않는다.

다음 준비 작업은 (1) 실험 비의존 하위 계약·오류 매핑·파일 목록 구체화, (2) 재현 명령·입력 사양·측정 방법과 모드별 판정 기준 완성, (3) yt-dlp 실행 경로 확보 및 버전에 맞는 의존성 확인, (4) 허용된 범위에서 최소 실험 수행·설계 반영 순서다. 음성 측정 특성 조사와 알고리즘 통과 판정을 분리하여 허용 범위를 결과를 본 뒤 유리하게 설정하지 않는다. Best 정렬·시간축 변환·FPS 확인 순서·Accurate 제한을 실험 없이 확정하지 않는다.

결론: 선행 Phase·소스·채택 정책 확인은 완료했으나 **전체 설계 확정 및 Phase 1 제품 구현 시작 준비는 미완료**다. 문서 수준의 계약 정리와 실험 절차 구체화는 계속 진행할 수 있다. 제품 코드·프로젝트 생성·패키지/도구 설치·영상 생성/다운로드·사이트 조회·취소 하네스 실행은 이번 점검에서 수행하지 않았다. commit/tag/branch 변경도 없다.

## 7. yt-dlp 외 준비 자료 구체화 — 2026-10-10

사용자가 yt-dlp 설치를 담당하고 나머지 준비를 요청했다. [하위 계약 통합](PHASE_1_CONTRACT_INTEGRATION.md)에 시간/JSON 숫자 처리, ProcessRunner 시그니처·바이트 상한·디코딩·중단/정리, 공유 미디어·실행 진단·출력 세션 호출, 오류 매핑, 단계별 제품/테스트 파일과 논리적 커밋 단위를 작성했다. [실험 실행 절차](PHASE_1_EXPERIMENT_RUNBOOK.md)에 로컬 CFR/소수 FPS/VFR/nonzero PTS 입력 사양·명령 초안, 사전 기대 프레임·음성 교정 공식, 사이트 설치 후 절차, 자식/파이프 재현 사양·기록 양식을 작성했다.

현재 완료한 범위는 **문서 수준의 계약·실험 절차 준비**다. 설치된 FFmpeg의 관련 필터 help와 공식 문서를 대조했지만 미디어 명령 실행 검증은 하지 않았다. 교정 오차 U의 공식과 고정 순서는 정했으며 수치 U는 실제 교정 후에만 기록한다. 실험 fixture/helper 생성과 전체 명령 실행 검증도 남아 있다. 신설 프로젝트나 제품 코드 없이 준비했고 기존 사용자 변경은 보존했다.

남은 사항: 사용자 설치 yt-dlp의 경로/버전 확인, E0~E3의 실제 실행·증거, 시간축/FPS 순서/포맷/자식 수명 보완의 결과 의존 계약 확정, 전체 통합 재검토다. 이미 채택한 일반 정책의 재승인은 요구하지 않는다. 문서 준비 완료를 실험 준비의 모든 조건 충족·전체 설계 확정·구현 완료로 표시하지 않는다.

문서 검증: 실행 절차의 PowerShell 블록 7개를 AST parser로 검사해 구문 오류가 없음을 확인했다. 실행한 것은 parser 검사이며 FFmpeg 인자·필터 표현식 실행 검증은 아니다. 보충 자료의 로컬 Markdown 파일 링크가 존재함을 확인했다. 신설 두 문서의 code fence 짝과 trailing whitespace를 확인했고 기준 commit 대비 제품 소스·솔루션·요구사항의 추적 변경은 없다. L1~L3의 사전 frame 경계는 정수 유리수 계산으로 재확인했다. git diff --check는 기존 추적 문서 범위에서 오류 없이 통과했으며 LF→CRLF 안내만 있었다. 미추적 문서는 별도 정적 검사 결과를 적용한다.
